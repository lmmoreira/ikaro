# 28 — Lock Catalog

> **When to load:** adding, changing or debugging a lock, a transaction that writes shared rows, a deadlock or a stuck request: every lock, its key, call sites, the required acquisition order and known hazards; why to pick each primitive is in `docs/ENGINEERING_RULES_BACKEND.md`.
> **Tags:** backend, database

**Audience:** any engineer or AI agent touching a transaction that writes shared rows, and anyone debugging a stuck request, a `40P01` deadlock or a duplicate/stale row.
**Scope:** every mechanism the backend uses to serialize concurrent work. BFF and web were searched too (`mutex`, `semaphore`, `redlock`, advisory/`FOR UPDATE` patterns) and hold none.
**Verified against the code** (docs-audit re-check of every lock, key, call site and §4 order, after M23-S49; read from the source, not reproduced in a running system; items marked **unverified** are reasoning from the code and need a concurrent test before anyone relies on them).
**How to keep it true:** a change that adds, removes or reorders a lock updates this file in the same commit (§7).

The *why* of choosing a primitive lives in `docs/ENGINEERING_RULES_BACKEND.md` § Choosing a race-condition primitive and § A lock only orders callers who both acquire it. This file is the *inventory*: what exists, what each one protects, and the order they may be combined in.

## 1. The mechanisms

| # | Mechanism | Shape of the race | Where it lives |
|---|---|---|---|
| M1 | Advisory lock, `pg_advisory_xact_lock(hashtextextended(key, 0))`, transaction-scoped | No row exists yet (or the invariant spans tables); purely cooperative, blocks only callers that take the same key | `ITenantLockPort` (`booking/application/ports/tenant-lock.port.ts`), adapter `typeorm-tenant-lock.adapter.ts` |
| M2 | Row lock, `SELECT … FOR UPDATE` / TypeORM `pessimistic_write` | The row exists and is read then written | repository methods named `…ForUpdate`, `lockBookingModels`, `findOpenBySourceForUpdate`, `countActiveManagersByTenant` |
| M3 | `FOR UPDATE SKIP LOCKED` plus a lease | Several workers draining one queue | `shared/infrastructure/outbox/typeorm-outbox.repository.ts` |
| M4 | Database constraint as the authoritative backstop | Two rows must never collide | migrations (`EX_…` exclusion, `UQ_…` unique) |
| M5 | Idempotency key | At-least-once delivery, the same work twice | inbox `ON CONFLICT (event_id, consumer_name) DO NOTHING`, outbox `UQ_shared_outbox_dedup_key`, the null-safe occupancy-assignment insert (`ON CONFLICT … DO NOTHING`, see the constraints table below), two `ON CONFLICT DO NOTHING` inserts with no conflict target (any unique violation skips the row): `persistQuestionRefs` in `typeorm-lead-form-submission.repository.ts` and `copyGlobalDefaultsForTenant` in `typeorm-notification-template.repository.ts`, and the timestamp-guarded `orUpdate` upsert in `typeorm-chatbot-provider-balance.repository.ts` (`recordCallOutcome`: an older timestamp never overwrites a newer one) |
| M6 | Optimistic concurrency (`version` column) | Two writers load the same aggregate and both save; no lock is held between read and write | `@VersionColumn` on `bookings`, `recurring_booking_schedules`, `availability_alerts`, `lead_form_configs` and `hotsite_configs` (the entity classes under `contexts/*/infrastructure/entities/`); the aggregate carries `version` and the repository's `save` UPDATE is version-checked. `billing.subscriptions` (built, M25-S08) has the same `version` column but no `@VersionColumn`: `typeorm-subscription.repository.ts` runs a conditional `UPDATE … WHERE version = :version` and treats zero rows as a concurrent modification |

The M1 adapter (`Tenant lock requires an active transaction`) and the M2 `…ForUpdate` / `lockBookingModels` methods (an error naming the method) throw when no transaction is open, and all of them are released on commit or rollback. **Exception: `countActiveManagersByTenant` (R5) does not throw — outside a transaction it silently falls back to an unlocked `repo.count`.** Every transaction opened by `runInNewTransaction` sets a transaction-local `lock_timeout` of 2s (`DB_LOCK_TIMEOUT_MS`, `shared/infrastructure/run-in-new-transaction.ts`; M23-S49, §5 H5), so a wait for any M1 or M2 lock (and for an uncommitted conflicting row under M4) that lasts longer than 2s fails with `TransactionContentionError`, which the caller sees as a retryable 503 `AUTH_TRANSACTION_CONTENTION` with `Retry-After: 1`; a deadlock victim (`40P01`) gets the same error. The timeout bounds **each** wait, not the whole transaction. M3 (`SKIP LOCKED`) never waits.

## 2. The order locks are taken in

A deadlock needs a cycle, so every transaction must take locks in the same order. This is the order the code follows **today**; take locks only downward and add a new lock at a stated level.

| Level | Lock | Notes |
|---|---|---|
| L-1 | Bookable-until lock, **shared** (B-U1, *built, M26-S18b*) | First lock of every Booking path that creates or moves a commitment; the plan save takes it **exclusive** after B-R1 (Billing ladder) |
| L0 | Tenant row (R3) | Only the settings and opening paths |
| L1 | Entity keys: `lockTenantDay`, `lockTenantStaff`, `lockCustomerAlerts`, `lockService` (A1, A2, A4, A5) | Never combined with each other in one transaction today |
| L2 | Service rows (R1, R2) | R2 batched and ordered by id |
| L3 | Resource advisory locks, `lockResources` (A3) | One call, ids sorted by the adapter |
| L4 | Future-commitment exception rows (R4) | Batched and ordered by id |
| L5 | Booking row | Taken implicitly by the `UPDATE` in `bookingRepo.save()`; no explicit lock exists |
| L6 | Occupancy rows | `release`, `assign`, `move`; the exclusion constraint M4 waits on a conflicting uncommitted row |

The Billing locks (B-A1 → B-R1 → charge rows) form their own ladder and never share a transaction with L0–L6; B-I1 (the account row) is taken alone, in its own transaction; see "Billing locks" below. The one lock both sides take is B-U1 (*built, M26-S18b; the exclusive side is taken by the plan save, M26-S19*): Booking holds it shared at L-1, the plan save holds it exclusive after B-R1. No Booking transaction takes B-R1 and no Billing transaction takes L0–L6, so the two ladders still cannot form a cycle.

The Loyalty balance row (R6) is a third, self-contained level: it is the first lock of a Loyalty transaction, and no Loyalty transaction takes any of L0–L6 or a Billing lock (`BookingCompleted` reaches Loyalty through the outbox and inbox, in its own transaction after the booking commits), so it needs no ordering against them.

**Rules that follow from the order**
- Several locks of one kind are taken in **one** call with a deterministic order, never one at a time in a loop.
- A lock orders only callers that also take it; after acquiring it, re-read the state it protects (a snapshot read before the lock is stale).
- **A lock taken in shared mode is the first lock of its transaction.** Postgres queues a new shared request behind a waiting exclusive one, so a shared request that comes after another lock can close a cycle with a holder of that other lock (a plan save waiting for a booking that waits for a resource lock held by a transaction that now waits for the shared lock). B-U1 is taken at L-1 in every Booking path, and the worklist path takes it before its resource locks for this reason.
- No network I/O inside a lock-holding transaction (CI-enforced `transactional-io`).
- A lock holder must finish well inside the 2s lock timeout, because every waiter fails after it. A path that legitimately holds a lock longer (a raise over a resource with many bookings, a long `end-recurring`) has to be made shorter or split before it ships; raising `DB_LOCK_TIMEOUT_MS` is the last resort, because the web gives up on the BFF at 8s and two waits must fit inside that.

**Known deviations from this order** are listed in §5 as hazards, not as accepted design.

## 3. Catalog

Each entry: what is locked, who takes it, the business case, why this primitive, where it sits in §2.

### Advisory locks (M1)

#### A1 — `lockTenantDay(tenantId, date)` — key `{tenantId}:{date}`
- **Taken by:** `OpenScheduleUseCase` (only when the opening is resource-scoped), `CloseScheduleUseCase`, `RemoveScheduleOpeningUseCase` (only when removing a tenant-wide opening).
- **Protects:** (1) two closures for overlapping windows on one date cannot both pass the overlap check (no DB constraint can express a time-range overlap here); (2) a resource-scoped opening cannot be created while its prerequisite tenant-wide opening is being removed.
- **Why advisory:** nothing to row-lock; the second use is a check-then-write across two tables.
- **Level:** L1 (taken after R3 in `OpenSchedule`).
- **Precedent:** M21-S03. **The key has no namespace prefix and cannot change:** a rolling deploy would run old and new keys side by side and silently stop serializing (`docs/ENGINEERING_RULES_BACKEND.md`).

#### A2 — `lockTenantStaff(tenantId, staffId)` — key `tenantstaff:{tenantId}:{staffId}`
- **Taken by:** `CreateResourceUseCase`, `UpdateResourceUseCase`, `ReactivateResourceUseCase`, `CascadeStaffDeactivationUseCase`.
- **Protects:** a STAFF-type Resource is never created, updated or reactivated against a staff member that a concurrent `StaffDeactivated` cascade is deactivating. Whichever side takes the lock first fully decides what the other sees.
- **Level:** L1. In the cascade and in reactivate it is followed by A3.
- **Precedent:** M21-S06.

#### A3 — `lockResources(tenantId, resourceIds)` — key `resource:{tenantId}:{resourceId}` per id
- **Taken by:** booking creation (`booking-request.helpers.ts` → `resolveAndCheckCandidates`), `DeactivateResourceUseCase` (through the raise below, after the resource `save()`), `ApproveBookingUseCase`, reschedule (`reschedule-quote.helpers.ts`), reassign (`resource-reassignment.helpers.ts`), `ReactivateResourceUseCase`, `RaiseFutureCommitmentExceptionsForResourceService`, the recurring request and approval (`recurring-considered-resources.helpers.ts`), `BookingSlotConflictService.assertSlotFree` and `lockResources`.
- **Protects:** the read-then-insert of resource occupancy. Two requests that both read a unit as free must not both take it, and a request choosing among interchangeable units must lock every candidate before reading (`resource-candidate-locking.helpers.ts`, M23-S32). Also orders a deactivation's impact read against a booking inserting occupancy on that resource.
- **Two-call shape (read again after the lock):** `lockOccupiedResources` in `booking-exception-closing.helpers.ts` takes the first set, re-reads the occupancy, and — only if the re-read found extra resource ids — calls `lockResources` a second time with the union. The adapter sorts the ids of each call, but the second call's order is not a continuation of the first: an id that sorts before one already held can be acquired later. It stays inside the one transaction and the 2 s lock timeout (a retryable 503) bounds a stall, but it is the one place this catalog's "one call, ids sorted" rule does not hold exactly.
- **Why advisory + a constraint:** the ids are sorted by the adapter (so overlapping sets cannot cross); the GIST exclusion M4-1 remains the authoritative backstop.
- **Level:** L3.
- **Also taken by (M23-S48):** every change that frees or moves a booking's occupancy — cancel (customer, staff), reject, end of a recurring schedule, the worklist's CANCEL (`saveTerminalBookingsInTransaction`), and approve and both reschedules, which add the resources the booking holds before the move to the same single call. A deactivation's raise and a cancel therefore meet on this lock.
- **Precedent:** M22-S03, M23-S32.

#### A4 — `lockService(tenantId, serviceId)` — key `service:{tenantId}:{serviceId}`
- **Taken by:** `RequestRecurringBookingScheduleUseCase`, `ApproveRecurringBookingScheduleUseCase`.
- **Protects:** the per-service cap on active `RESOLVE_PER_OCCURRENCE` schedules (count then insert), which has no concrete resource to lock yet.
- **Level:** L1, then R1, then A3 (see §4).
- **Precedent:** M23-S04.

#### A5 — `lockCustomerAlerts(tenantId, customerId)` — key `availability-alerts:{tenantId}:{customerId}`
- **Taken by:** `CreateAvailabilityAlertUseCase`.
- **Protects:** the per-customer active-alert cap (count then insert; no alert row exists yet).
- **Level:** L1, then R1.
- **Precedent:** M23-S06.

### Row locks (M2)

#### R1 — Service row, `serviceRepo.findByIdForUpdate`
- **Taken by:** `ActivateService`, `DeactivateService`, `UpdateService`, `UpdateServiceLegs`, `UpdateServiceResourceRequirements`, `UpdateServiceBookingPolicy`, `UpdateServicePublicPage` (TD56-S03; it also reads other services' slugs while holding the row, but two first publishes of different services hold different rows, so cross-service slug uniqueness rests on the partial unique index `UQ_booking_services_tenant_public_slug`, not on this lock), `PublishServiceIntakeSchema`, `CreateAvailabilityAlert`, `RequestRecurringBookingSchedule` (inside `prepareRequest`).
- **Protects:** lost updates, because `save()` wholesale-replaces the service's child tables; and a stale eligibility or policy read in a request that depends on it.
- **Level:** L2.

#### R2 — Service rows, batched, `serviceRepo.lockBookingModels(ids)` (`ORDER BY id`)
- **Taken by:** one-off booking creation (`lockAndVerifyServiceModels` in `booking-request.helpers.ts`).
- **Protects:** a service's `bookingModel` cannot change while its first booking is being created (UC-056 immutable-after-history). Re-checks the fresh model against the pre-transaction snapshot.
- **Level:** L2. Booking creation takes it before A3, the same order as the recurring request (M23-S48, was the reverse: hazard H1).
- **Precedent:** M22-S01, PR #479 (the first version lacked `ORDER BY` and was caught in review).

#### R3 — Tenant row, `tenantRepo.findByIdForUpdate` (bypasses `CachingTenantRepository`)
- **Taken by:** `UpdateTenantSettingsUseCase`, `UpdateHotsiteContentUseCase`, `GetTenantBusinessHoursForUpdateUseCase` (reached from `OpenScheduleUseCase` through `BookingPlatformPort.getBusinessHoursAndLocaleForUpdate`).
- **Protects:** narrowing `businessHours` while `OpenSchedule` validates against it; lost updates of hotsite content.
- **Why a row lock, not advisory:** the row exists, and an advisory lock still reads through the cache regardless of order.
- **Level:** L0.
- **Precedent:** M21-S03 PR #460 (an advisory-lock design was walked back).

#### R4 — Future-commitment exception rows
- **`findByIdForUpdate`:** `ResolveFutureCommitmentExceptionsUseCase.lockOpenEntry`, `DismissFutureCommitmentExceptionsUseCase`. Two managers acting on one entry: the second waits, then sees it closed.
- **`findOpenBySourceForUpdate`:** `ReactivateResourceUseCase`. Batched, `ORDER BY id`. A reactivation closing a resource's own entries cannot race a manager resolving one.
- **`findOpenByAffectedForUpdate` (M23-S48):** the terminal helper (`saveTerminalBookingsInTransaction`) and approve/reschedule. One batched query for the booking(s), `ORDER BY id`. A cancel closing a booking's entries cannot race a manager resolving one.
- **Level:** L4. The worklist's resolve takes A3 before it for CANCEL and RESCHEDULE; REASSIGN takes no A3 first because its lock set (the candidate targets) never contains the deactivated source (H2).
- **Precedent:** M23-S08, M23-S45.

#### R5 — Active managers of a tenant, `countActiveManagersByTenant`
- **Taken by:** `DeactivateStaffUseCase`, `UpdateStaffProfileUseCase`.
- **Protects:** the last-active-manager guard. Locks every active MANAGER row of the tenant (`FOR UPDATE` cannot be combined with `COUNT`, so ids are selected and counted in code).
- **Level:** none of the above; it only touches `staff.staff`. The query has `ORDER BY id` since M23-S48 (H3).
- **Only locks inside a transaction:** outside one, the repository falls back to an unlocked `repo.count`, with no error. Both callers run inside `txManager.run` today; a new caller must too.

#### R6 — Loyalty balance row, `balanceRepo.findByCustomerForUpdate` / `findOrCreateByCustomerForUpdate` (TD60-S00)
- **Taken by:** `CompleteBookingLoyaltyEffectsUseCase` (`findOrCreateByCustomerForUpdate`), `RedeemPointsUseCase` and `ExpirePointsJob.processGroup` (`findByCustomerForUpdate`, one transaction per customer). Both methods throw outside a transaction.
- **Protects:** the lost update of `loyalty.loyalty_balances.current_points`, which the three writers each read, change in memory and `upsert` as an absolute value: a redemption read before an expiry commits resurrecting the expired points, two redemptions spending the same points, two earns losing one. Redeem, earn and the sweep are serialised per `(tenant_id, customer_id)`; different customers never wait on each other.
- **First earn:** when no row exists `FOR UPDATE` locks nothing, so `findOrCreateByCustomerForUpdate` selects with the lock first, and only on a miss runs `INSERT … ON CONFLICT DO NOTHING` and selects again with the lock. A second first earn parks on the first one's uncommitted insert, then locks the committed row. The common path (row exists) is one query.
- **Re-checks under the lock, on the transaction's own connection:** what was decided before the lock is checked again after it. The earn re-checks the inbox (`inboxRepo.hasBeenProcessed`, a duplicate discount-only `BookingCompleted` has no earn line whose unique key could fail) and the sweep re-checks its entries with one batched `expiryLogRepo.findProcessedEntryIds` (an overlapping run may have expired them, and `markProcessedMany` is `ON CONFLICT DO NOTHING`, so it never conflicts). Both read through the active transaction's manager, so a writer holding the row never takes a second pooled connection while it waits.
- **Level:** its own, first in the Loyalty transaction (§2).
- **Precedent:** TD60-S00.

### Billing locks (B-R1 built by M25-S08, B-A1 by M25-S09, B-C1 by M26-S02, B-I1 by M26-S16; B-Q1's index built by M25-S03, its purge job still planned; B-P1 still planned — documented ahead of the code)

The Billing context (`docs/BOUNDED_CONTEXTS.md` § 7) adds five locks (B-A1, B-R1, B-C1, B-I1, B-P1) and one unique constraint (B-Q1). They live in the `billing` schema and **never combine with L0–L6 in one transaction** (Billing never opens a Booking transaction; the one lock the two sides share is B-U1, below, which carries no row), so they form their own small ladder: B-A1 (advisory) is taken before any row exists and in its own transaction; inside a subscription transaction the order is B-R1 → B-C1 (charge row). B-R1 (M25-S08, the `findByTenantIdForUpdate` port method) and B-A1 (M25-S09, the `lockSignupRegistration` port method) are implemented; until the code for the others lands this section is their design, and the `lock-catalog-coverage` check enforces a name once its port method exists.

#### B-A1 — signup registration, key `signup:{googleSub}`
- **Taken by:** `ReserveSignupRegistrationUseCase` behind `POST /internal/billing/registrations` (the self-signup eligibility check, UC-127), through the Billing-local port method `ISignupRegistrationLockPort.lockSignupRegistration(googleSub)` (adapter `TypeOrmSignupRegistrationLockAdapter`, M25-S09). An `OPERATOR` registration takes no lock: it has no Google `sub` and runs no eligibility check.
- **Protects:** the trial-eligibility check (read earlier registrations of this Google `sub`, then insert a `RESERVED` row) — no row exists yet for the new signup, so there is nothing to row-lock and no constraint can express "all earlier self-signup tenants of this `sub` have paid". Two concurrent signups of one Google account must not both pass.
- **Why advisory:** nothing exists yet. The key is **new** and may be namespaced freely (`signup:` prefix); transaction-scoped, the M1 mechanism: `pg_advisory_xact_lock(hashtextextended('signup:' || googleSub, 0))`.
- **Level:** B-A1, alone in its transaction.
- **Limit (tax-id half of the one-trial rule):** B-A1 locks only the Google `sub`, so the cross-Google-account tax-id check (the normalised CPF/CNPJ already belongs to a never-paid `billing_accounts` row) is **best-effort under concurrency**: two simultaneous signups with different Google accounts and the same tax id can both pass. Stated, not hidden (M26-S24); the hard anti-abuse controls are Turnstile, the per-`sub` rule here and the per-tax-id check on the common, non-concurrent path.

#### B-R1 — subscription row, `subscriptionRepo.findByTenantIdForUpdate`
- **Taken by:** every use case that changes a subscription's status or period: payment confirmation (webhook, reconcile and on-demand refresh), the status sweep (one transaction per subscription), the charge issue job (one transaction per subscription, M26-S05: it inserts the `PERIOD` charge and advances `next_due_date`, so it serialises with a plan save and a webhook), cancel and reactivate, plan save and confirm, and the operator suspend / unsuspend / exempt / grace actions (built in M25-S15b: `loadSubscriptionForUpdate` in `application/helpers/operator-billing.helpers.ts` is the one place the four take it). The `TenantProvisioned` handler does **not** take it: no subscription row exists before its first insert, so a redelivery is a no-op through `UNIQUE(tenant_id)` (`UQ_billing_subscriptions_tenant`), not through a lock.
- **Protects:** a paid charge may move the subscription back to `ACTIVE` — two aggregates (`Charge` and `Subscription`) in one use case. A payment that arrives while the sweep is deciding to suspend must win ("the paid state wins"); two webhooks for one charge, or a webhook and a manager's cancel, must not interleave. `Subscription.version` (M6) is the second line of defence. Status is recomputable (the reconcile job re-derives it), so the invariant does not depend on this lock alone.
- **Why a row lock:** the row exists and is read then written.
- **Why it is taken by tenant id:** `UNIQUE(tenant_id)` makes the tenant id the row's natural key, and every taker already has it (the operator routes carry it, the webhook resolves it from the provider customer, the sweep selects `(tenant_id, id)` pairs). One locking query replaces an unlocked read followed by a lock by id, and there is no second UUID argument to swap. The method locks the subscription row (`FOR UPDATE`) and then loads the aggregate's items in the same transaction; the items need no lock of their own because every writer takes the parent row lock first, and the read is always made after the lock, so a snapshot read before it is never reused.
- **Level:** B-R1, then the charge rows are written through `chargeRepo.save()` (their `UNIQUE` indexes are the backstops, below). No provider I/O inside the transaction (CI-enforced `transactional-io`).
- **Test:** § 3.1 — `typeorm-subscription.repository.integration` › two concurrent lockers serialise (M25-S08, mutation-checked). `findByTenantIdForUpdate` throws outside an active transaction, and `save()` still checks the optimistic `version` (`SubscriptionConcurrentModificationError`) as the second line of defence.

#### B-C1 — charge row, `chargeRepo.findByIdForUpdate`, and several at once, `chargeRepo.findByIdsForUpdate` *(built, M26-S02; the batched form M26-S06)*
- **Taken by:** every use case that changes an existing charge, **after** B-R1 when it also changes the subscription (payment confirmation through `ApplyChargeFactService`, the status sweep, cancel, reactivate, plan save), and the short transactions that follow a provider call: store `READY` (a creation failure writes nothing: the claim already counted the attempt), clear `provider_cancel_pending`, and *(built, M26-S15)* store a regenerated payment link and record the payment return, both **B-C1 alone, no B-R1** (they change charge columns and read nothing from the subscription). Those re-read the charge under the lock instead of saving a copy loaded before the provider call. The insert of a new charge takes no lock (its `UNIQUE` indexes are the backstops).
- **Protects:** a stale copy of a charge must never overwrite a newer one. The case that exists: the creator inserts the charge `PENDING` and calls the provider; a webhook marks it `PAID` in between; the creator's later `READY` write must not put `PENDING` back (and must still store the provider id and link, `markCreationReady` is legal on a `PAID` or `CANCELED` charge). The `READY` write takes B-R1 first (the order of the ladder) only to read the exemption under the subscription lock: a tenant exempted while the provider call was in flight gets the charge cancelled and flagged for the cancel retry instead of announced; the other post-provider-call writes run without B-R1, which is why the subscription lock alone is not enough.
- **Why a row lock:** the row exists and is read then written. `billing.charges.version` is the second line of defence (`ChargeConcurrentModificationError`, `save()` writes only the mutable columns, never the claim columns), the same shape as B-R1 and `Subscription.version`.
- **Not taken by the creation claim:** `claimForProviderCreation` is one conditional `UPDATE … FOR UPDATE SKIP LOCKED` sub-select on its own autocommit statement; a caller that finds the row locked is simply not the owner. It does not bump `version`.
- **Level:** after B-R1, never before (subscription → charge rows, M26-D2). The one path that locks two charge rows in a transaction is `ApplyChargeFactService` when a stale `PERIOD` charge is paid for a payment-suspended tenant (M26-S04): the paid charge first, then the tenant's open `RECOVERY` charge to cancel it, always in that order, and no other path takes the recovery charge's lock before a `PERIOD` charge's. No provider I/O inside the transaction (CI-enforced `transactional-io`). Throws outside an active transaction.
- **Several charges at once, `findByIdsForUpdate` (M26-S06):** a path that must lock more than one charge of a tenant takes them in **one** query, `WHERE tenant_id = :t AND id IN (…) ORDER BY id FOR UPDATE`, never one `findByIdForUpdate` after another (the multi-row rule of `docs/ENGINEERING_RULES_BACKEND.md` § Choosing a race-condition primitive): one round trip while the subscription row is held, and one deterministic order, so two batches that overlap in opposite orders park on each other instead of deadlocking. The status sweep takes every open charge of the subscription, and the current trial's first invoice, this way before it judges any rule.
- **Test:** § 3.1 — `typeorm-charge.repository.integration` › `findByIdForUpdate` serialises two concurrent lockers (M26-S02, mutation-checked); `typeorm-charge.repository.sweep.integration` › `findByIdsForUpdate`: two overlapping batches asked in opposite orders serialise on the rows and the second sees the first's committed state (M26-S06, mutation-checked).

#### B-I1 — billing account row, `accountRepo.findByTenantIdForUpdate` *(built, M26-S16)*
- **Taken by:** `UpdateBillingIdentityUseCase` (`PUT /billing/identity`, UC-118), as the first read inside the `txManager.run()` that also saves. The identity read (`GetBillingIdentityUseCase`) takes no lock.
- **Protects:** `billing_accounts` has no `version` and `save()` rewrites every column. Two writers touch the row: the manager's identity save (whole-row `save()` of a copy it read) and the charge issue job's `assignProviderCustomer` (S05: a column-scoped `UPDATE` of `provider` and `provider_customer_id`, committed before the charge is created). Without the lock a save that read the account before that `UPDATE` and wrote after it puts `NULL` back: the customer binding is lost, the next charge creates a second provider customer and its webhooks cannot be traced to the tenant. Two saves of different fields from two tabs would overwrite each other the same way.
- **Why a row lock:** the row exists and is read, then written. The alternative, a column-scoped `saveIdentity()` with no lock, would close only the first race, and the address merge needs a consistent read of the stored address.
- **Level:** alone in its transaction. It never combines with B-R1 or B-C1: the account's country is read from the subscription row, which is immutable, without a lock. `assignProviderCustomer` is a single statement that waits for the holder and then updates the committed row, so it can sit behind B-I1 without taking any lock itself, and no cycle exists.
- **Port:** `IBillingAccountRepository.findByTenantIdForUpdate(tenantId)` (adapter `TypeOrmBillingAccountRepository`, second adapter `InMemoryBillingAccountRepository`). It throws outside an active transaction, like the B-R1 and B-C1 readers.
- **Test:** § 3.1, `update-billing-identity.use-case.integration` › the B-I1 tests (mutation-checked: reading through the plain `findByTenantId` fails both).

#### B-U1 — bookable-until lock, key `bookable-until:{tenantId}`, shared / exclusive *(built, M26-S18b; its exclusive taker, the plan save, is M26-S19)*
- **Taken by (shared, `lockCommitmentsShared`):** every Booking path that creates or moves a commitment, through the one guard `BookableUntilGuard`: one-off booking creation (public, authenticated, staff), customer and staff reschedule, approve with a new time, the worklist's RESCHEDULE, the recurring-schedule request (customer, staff on behalf, renewal), alert create and update. The guard takes it first in the transaction, then reads `bookableUntil` uncached and applies the pure rule. **Taken by (exclusive, `lockCommitmentsExclusive`):** the plan save (S19), after B-R1, around the removal guard (S18a), the scheduled-removal write and the commit.
- **Protects:** the check-then-act race between "a booking reads `bookableUntil = null`" and "the plan save counts what blocks a removal". Whichever side takes the lock first fully decides what the other sees: a booking is either committed before the count (the count sees it) or starts after the commit (it reads the cap). Counting under B-R1 alone cannot close it, because Booking's writes do not take B-R1.
- **Why advisory, why shared:** nothing exists to row-lock (a booking is about to be created), so it is primitive 3 (`pg_advisory_xact_lock`). The Booking side takes the **shared** mode (`pg_advisory_xact_lock_shared`), so bookings never wait for each other; only the rare plan save is exclusive and waits for the bookings in flight (milliseconds), after which new bookings queue behind it. Postgres queues a shared request that arrives after a waiting exclusive one, so the save cannot starve. A key that is new may be namespaced freely, and this one is, from day one.
- **Level:** L-1 for Booking (before R3 / L1…), after B-R1 for the plan save. No Booking transaction takes B-R1, so the two orders cannot cross.
- **Only callers that take it are ordered.** A new commitment path that skips `BookableUntilGuard` reopens the race and nothing fails; the guard is the one place that takes the lock, so a route cannot apply the cap without it. A mechanical `architecture-check` rule is not built.
- **Port:** `shared/ports/bookable-until-lock.port.ts` (`BOOKABLE_UNTIL_LOCK_PORT`; adapter in `shared/infrastructure`; both Billing and Booking take it, so it belongs to neither). It throws outside an active transaction like the other advisory ports.
- **Test:** § 3.1 — three contract tests in `bookable-until-lock.integration.spec.ts` (an exclusive holder makes a booking wait, then refuse; a shared holder makes the exclusive acquirer wait and it then sees the booking; two shared holders do not wait for each other), each mutation-checked in M26-S18b (guard without the lock: the first fails; shared made exclusive: the third fails; shared a no-op: the first, second and the transaction check fail).

#### B-P1 — price-list rows, one batched `FOR UPDATE` *(M26-S38)*
- **Taken by:** the operator price-change use cases (create, exact version, percentage adjust, dry run excluded): one batched query locks every affected `billing.feature_prices` row `ORDER BY id` before the dry-run hash is re-verified and the `feature_price_versions` rows are written; it never combines with B-R1 in one transaction (price writes touch no subscription).
- **Protects:** two concurrent adjustments (or an adjustment and an exact change) of the same prices must not interleave: `BILLING_PRICE_BATCH_CHANGED` is decided against the locked state, and `UNIQUE(feature_price_id, effective_from) WHERE superseded_at IS NULL` is the backstop.
- **Why a row lock:** the rows exist and are read, then written (the multi-row rule: one batched query, deterministic order).
- **Level:** alone in its transaction. Named test: two concurrent adjustments serialise and the second returns `409 BILLING_PRICE_BATCH_CHANGED`.

#### B-Q1 — purge job, `UNIQUE(tenant_id) WHERE status <> 'COMPLETED'` *(slice G)*
- One in-flight erasure per tenant; a second `TenantPurgeRequested` for the same tenant hits the constraint and is a no-op (M4). Participant completions are idempotent per `(job, participant)`.

### Queue lease (M3)

#### Q1 — Outbox claim
- `shared.outbox` rows are claimed with `FOR UPDATE SKIP LOCKED` plus `lease_token` / `lease_expires_at`; a worker that dies releases the claim when the lease expires. Several relay instances can run side by side.
- A second claim path exists: the inline per-id claim (`CLAIM_UNPUBLISHED_BY_ID_SQL` in the same repository) is a plain conditional `UPDATE` guarded only by `lease_expires_at IS NULL OR < now()`, with no `SKIP LOCKED`. Only the sweep uses `SKIP LOCKED`.

### 3.1 Which test proves each lock

A test counts as coverage for a lock only if **removing the lock makes it fail** (the mutation check in `docs/ENGINEERING_RULES_TESTING.md` § Concurrency tests). Kinds: **contract** = hold the lock, start the use case, prove it waits (and, for a resource lock, that it does not already own the worklist entry row); **outcome** = assert the data the lock protects; **race** = two real operations at once, a few rounds, assert the invariant. ## 5. Known hazards (each one is reading, not a reproduced incident)

| ID | Hazard | Status |
|---|---|---|
| H1 | **Service row versus resource order is inverted.** One-off booking creation takes A3 then R2; the recurring request takes A4 → R1 → A3. A one-off booking holding resource R and waiting on service row S can deadlock with a recurring request holding S and waiting on R. Postgres aborts one with `40P01`. | **Closed in M23-S48:** one-off creation locks the service rows before it resolves candidates (call order pinned by a unit test). A race test (`recurring-booking-schedule-approval` › a one-off booking and a recurring request on the same service and room never deadlock) fails when the old order is restored, so the deadlock was real. |
| H2 | **Resolve versus reactivate.** Resolve REASSIGN/RESCHEDULE take the entry (R4) then resource locks (A3); reactivate takes A3 then R4. The cycle needs the failing resolve case (a `CUSTOMER_CHOICE` pinned to the deactivated resource); reassign locks only candidate targets. | **Closed in M23-S48:** RESCHEDULE locks the full resource set before the entry row; an integration test shows it waits for a held source-resource lock without holding the entry row, and a unit test pins that REASSIGN never asks for the source. The reschedule resolves from the same snapshot of the tenant's resources that the pre-lock read (`ResolutionSnapshot`), so a resource that becomes eligible in between is neither chosen nor locked; a unit test adds a room between the resource locks and the entry lock and checks that no later lock request leaves the held set. |
| H3 | `countActiveManagersByTenant` locks manager rows with no `ORDER BY`; two concurrent deactivations rely on identical scan order. | **Closed in M23-S48** (`ORDER BY id`). A lock-contract test holds an uncommitted manager deactivation and checks that the last-manager guard waits for it, then refuses with `LastActiveManagerError` (the earlier two-request race passed without the lock and was replaced). |
| H4 | Cancel, reject and end-recurring take no resource lock, so a stale future-commitment entry can be inserted by a concurrent raise. | **Closed in M23-S48** (A3 → R4 → booking `save`); cancel racing a deactivation, and cancel racing the worklist's CANCEL, are covered by integration tests. |
| H5 | **No `lock_timeout` or `statement_timeout` anywhere in the backend** (before M23-S49) (search over `*.ts` and infra found none). A deadlock is detected by Postgres after `deadlock_timeout` and one side fails with `40P01`, which no code maps; a merely slow holder (a raise over a resource with many bookings, a long `end-recurring`) makes others wait without bound. | **Closed in M23-S49** (design, why 2s and the retry contract: the "Lock waits are bounded (M23-S49)" paragraph in `docs/ENGINEERING_RULES_BACKEND.md`, near the top). A `40P01` deadlock is still a real defect to fix by ordering (§2); the 503 only makes it visible and retryable instead of a 500. |
| H6 | **Booking creation, approval and reschedule (the customer's, the staff's and the worklist's) read closures and openings without the tenant-day lock (A1).** `CloseScheduleUseCase` takes A1 and these paths take only R2/A3 (and R4), so a closure can commit while a transaction that has already read "no closure" is in flight, and that booking lands inside the closure. | **Accepted (TD50).** It is indistinguishable from the booking having been made, approved or moved a moment before the closure, which is always allowed: closing a day does not read or act on existing bookings. ## 6. Debugging a stuck request or a deadlock

- **`40P01 deadlock detected`**: the Postgres log names both statements and the two lock targets. Find the two use cases in §4 and compare their sequences with §2.
- **A request returns 503 `AUTH_TRANSACTION_CONTENTION`** (with `Retry-After: 1`): it waited longer than 2s for a lock, or Postgres chose it as a deadlock victim; nothing was written. The backend logged a `warn` "Transaction aborted by lock contention" with the `sqlState` (`55P03` timeout, `40P01` deadlock) and, inside an HTTP request, the tenant and correlation ids. Find the holder with the query below while it is still running; for a `40P01` the Postgres log names both statements.
- **A request hangs**: no single lock wait lasts more than 2s (H5 closed), but a request that waits on several locks in turn can still exceed 2s in total, and a long wait can also be a slow statement or an exhausted pool; find the blocked and blocking sessions.
  ```sql
  SELECT l.pid, l.locktype, l.classid, l.objid, l.granted, a.state, a.query_start, a.query
  FROM pg_locks l JOIN pg_stat_activity a USING (pid)
  WHERE l.locktype = 'advisory' OR (l.locktype = 'transactionid' AND NOT l.granted);
  ```
- **Which advisory key is it?** The key is `hashtextextended('<key>', 0)`, a bigint split into `classid` (high 32 bits) and `objid` (low 32 bits). Compute `SELECT hashtextextended('resource:<tenantId>:<resourceId>', 0)` and compare with `(classid::bigint << 32) | objid`. Key formats are in §3.
- **A duplicate or stale row**: check which constraint in §3 should have stopped it and which use case in §4 should have taken the lock; a path that releases or writes without taking the lock is the usual cause.

## 7. Adding or changing a lock

1. Pick the primitive by the shape of the race (`docs/ENGINEERING_RULES_BACKEND.md`): a constraint if the rows can express it, a row lock if the row exists, an advisory lock if nothing exists yet.
2. Choose its level in §2. If it must be taken against the order, say why in the PR and add the concurrent test that proves no cycle.
3. Batch several locks of one kind into one call with a deterministic order.
4. After acquiring, re-read the state the lock protects.
   - A lock with a **shared** mode also takes the first position of its transaction (§ 2). Prove the pairing with a test whose shared holder saves a real row and whose exclusive side counts it after the release (the second test of `bookable-until-lock.integration.spec.ts`); a shared holder that only holds the lock proves the order, not the outcome.
5. A new advisory key is free to namespace; an existing live key never changes.
6. Add the entry to §3, the sequence to §4, and any hazard to §5, in the same commit. `pnpm architecture-check` (`lock-catalog-coverage`) fails when a port's `lock*()` or `*ForUpdate()` method is not named in this file; it checks the name only, so the order and the test are still yours.
7. Ship a concurrent integration test; a unit test with an in-memory double proves nothing about ordering.
8. Name the test in § 3.1 and run the mutation check on it: remove the lock and watch it fail. A test that passes without the lock is not coverage (R1 is the example); if no test can tell, record that in § 3.1 and say why.
