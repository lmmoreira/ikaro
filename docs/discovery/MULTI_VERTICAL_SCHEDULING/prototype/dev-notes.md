# Dev Notes — Multi-Vertical Scheduling Discovery Prototype

**Status:** Discovery-stage, illustrative. Lighter than a `plan/journey/` prototype's dev-notes — no full state-coverage checklist, no mandatory unhappy-path variants. Purpose is to show direction, not to be implementation-ready.

Full model: `../MULTI_VERTICAL_SCHEDULING.md`. Full candidate use-case list: `../MULTI_VERTICAL_SCHEDULING_USECASES.md`. Full data model (tables, constraints, migration ordering): `../MULTI_VERTICAL_SCHEDULING_DATA_MODEL.md`.

## What's real vs. invented here

- **Real:** `--ba-*` tokens, dashboard shell (sidebar/topbar/bottom-nav/bottom-sheet), card/form/badge conventions — all copied from `plan/journey/shared/` and existing staff/manager prototypes, unmodified.
- **Invented:** the tenant "Vitta Studio" and all its data (staff names, service names, prices, capacities, session times). Chosen so one resource (Camila Duarte) can plausibly be both a hair stylist (1:1) and a Pilates instructor (capacity 4) — the concrete instance of discovery §2 model #13.
- **New nav items, not in today's IA:** "Recursos" (manager-only, like Equipe/Configurações/Hotsite) and "Turmas" (staff+manager, like Serviços).

28. **Every eligibility checklist on `manager-02` was checked against the tenant's actual full resource list and found incomplete — fixed (2026-08-05).** Asked directly: if there's no structured "purpose" concept behind any of these pools (item 26), doesn't that mean every checklist needs to show the *complete* resource list, since an incomplete one is indistinguishable from a correct one? 29. **Several exclusion reasons conflated "already allocated elsewhere" with "not suited for this purpose" — fixed (2026-08-05).** Asked directly whether "Kit Halteres — usado por CrossFit, não elegível" was excluding it *because* another service already claimed it, given there's no structured purpose concept (item 26): yes, and that's backwards. Suitability (is this resource the right kind of thing for this purpose?) and allocation (is it currently free?) are different questions — allocation is what `resource_occupancy` handles; a pool declaration should only ever answer suitability. Taken literally, "usado por CrossFit" implies Kit Halteres would become a sensible massage choice the moment CrossFit's template were deleted, which is absurd — dumbbells were never suited to massage regardless of who else uses them. Replaced every "usado/usada por X" and bare "não elegível" reason with the resource's actual physical nature (e.g. Kit Halteres → "equipamento de musculação, não utilizado em massagens"; Estúdio 1/2 → "salão aberto de Pilates, sem privacidade/estrutura para massagem ou sauna"), applied consistently everywhere that resource appears excluded, regardless of which checklist is asking.

30. **`slot_index`/`requirement_index` removed as premature abstractions, then swept for staleness across every doc (2026-08-05).** Asked directly whether grouping by `resource_type` alone would work instead of a stored ordering column — checked every worked example across all four affected tables (`service_resource_requirements`, `service_leg_resource_requirements`, `service_class_resource_pool`, `class_schedule_template_slots`) and found none ever need two resources of the same type in one bundle/leg/slot-set; the one justification that had seemed to require it (a template needing two `ROOM` slots) was a misremembered citation of an already-different, already-resolved case (model #6's two-templates answer). Removed the column from all four tables plus `class_session_resources`; `resource_type` (4 fixed values) is the natural key instead. Display order doesn't need a stored column either — Postgres gives no row-order guarantee regardless, so a fixed `ORDER BY CASE resource_type` or an application-side priority list achieves the same result more simply. Followed by a full sweep for anything else this session's corrections had left stale: found and fixed the domain doc's §8 aggregate-deltas table (still listing `ClassSessionBooking`'s old 3-state enum instead of the current 5-state one, and missing `Service.classResourceSlots` entirely), and CAND-24/CAND-25 in the use-cases doc (still describing `waitlistPosition` as an assigned/stored/shiftable field after the domain doc had already been corrected to describe it as derived). `(slot 0)`/`(slot 1)` labels removed from `manager-02`'s Aula de Pilates checklist example.

## What this prototype still deliberately does NOT cover

- Unhappy-path variants (loading/error/empty states) — none created. If this direction is promoted to a real `plan/journey/` prototype, those become mandatory per that folder's README.
- A full "Serviços" or "Horários" list screen — sidebar/bottom-nav items not central to this discovery point to `#` placeholders.
- Session-cancellation refund policy (staff-02) — still an open question, surfaced visibly on purpose (see discovery doc §9), not answered here.
- CAND-12 (edit/deactivate a template) and CAND-02/04/05 (resource working-hours editor, resource-scoped closure/opening) — still no dedicated screens; lower priority than the four closed above since they're closer to today's existing settings-editor patterns and less novel.
- CAND-23b (customer cancels a single one-off class booking, added 2026-08-05) — no dedicated screen yet either; same priority tier as CAND-12/CAND-02/04/05 above.
- Credit-passes and time-based memberships — explicitly deferred; see `MULTI_VERTICAL_SCHEDULING.md` §11's extension-point note for why today's shape needs no rework to receive either, once that story is actually scoped.

## If this gets promoted to a real journey

Per `CLAUDE.md` §15: run `/docs-audit` clean first, then write the actor `<slug>.md` + update `use-cases.md` + `plan/journey/README.md`'s index — *before* creating any file under `plan/journey/<actor>/prototypes/`.
